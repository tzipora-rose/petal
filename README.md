# petal

An MCP server that runs shell commands for Claude Code in shells that keep their state between calls: PowerShell 7, Windows PowerShell 5.1 and Git Bash. Variables, functions, the folder and environment variables carry over from one command to the next, as in a terminal. Before running a command it checks it for a few known traps; when it finds one it does not run the command, and says what it found.

Windows only, built with Zig 0.16, no dependencies. It speaks MCP over standard input and output, one JSON-RPC message per line, written by hand. It installs nothing, downloads nothing and sends nothing anywhere.

## Tools

- **`run`**: runs `command` in a shell. `shell` is `pwsh` (PowerShell 7, the default), `powershell` (Windows PowerShell 5.1) or `bash` (Git Bash). `timeout` is in milliseconds: 600000 (10 minutes) by default, at least 1000, at most 14400000 (4 hours). `intended: true` runs a command the check stopped, exactly as written. `stamen` and `from` are below.
- **`shells`**: the session's stamens and, for each of their shells, whether it is running, idle or busy (with what, since when), its folder, how many commands it has run, and the folder holding the session's log and outputs.
- **`restart`**: ends a shell of one of the caller's stamens, with everything it started, and starts it fresh in the folder it was in. Without `shell`, every running shell of the stamen. A busy shell is not restarted.

`run` and `restart` do not declare themselves read-only, so Claude Code sends one agent's calls to them one at a time. `shells` does.

## Stamens: each agent's own shells

A stamen is one agent's set of shells: one of each kind, each started the first time it is used. The main agent's stamen is `main`; a subagent's is its agent id. The agent comes from petal's hook (below), which writes it into each call; without the hook every call uses `main`, and the first reply says so.

- An agent can open further stamens of its own by name: `stamen: "build"` is the stamen `<agent>:build`. A name uses letters, digits, dot, dash and underscore, at most 64 of them.
- **A shell runs one command at a time.** A call to a busy shell is answered at once with what it is busy with, since when, and how to use another stamen.
- **`from`** starts a stamen's shell in another stamen's folder with its environment variables, as of that shell's last finished command, when the call starts that shell. Variables and functions are never copied: in PowerShell, objects cannot be copied with their behavior, so a copy would be a different value with the same name.
- A stamen other than `main` that runs no command for 30 minutes has its shells ended. Used again, it starts fresh, and the reply says so.

## How a command runs

- **PowerShell**: petal starts the shell with `-NoLogo -NoProfile -NonInteractive -OutputFormat Text` and its loop, `src\loop.ps1`. Every command runs in the global scope. Requests arrive on a pipe whose handle number the loop is given; the shell's standard input is `NUL`, so no program a command starts can read them. Output, errors, warnings, verbose and debug lines are merged in the order they are written and rendered as the console shows them (`Out-String -Width 200`), each with its prefix (`WARNING:`), without trailing spaces. While a command runs, the console's code page is UTF-8, so programs' output is read as UTF-8.
- **Exit codes in PowerShell**, as Claude Code's own PowerShell tool reports them: `$LASTEXITCODE` when a program ran during the command, else 0, or 1 when the command's last statement failed. `$LASTEXITCODE` starts empty in each command, as in a new PowerShell; when a command runs no program, it gets back the value it had.
- **After each PowerShell command, before replying, petal runs a full garbage collection** and waits for the objects it frees to close their files.
  - Why: a .NET reader a command leaves open, such as a `[IO.File]::ReadLines` loop ended by `break`, holds its file until a collection frees it, and lets no other program write to it meanwhile. In a shell that lives on, that collection can come an hour later. Claude Code writes the call's result to its transcript right after the reply, and a write refused then leaves the record out of the transcript until the session's next compaction writes it again, or for good if that compaction keeps no newer message or the session ends first (the check's fifth rule, below).
  - Cost: about 10 ms per command, and about 0.1 s when the shell holds a few hundred MB.
  - A reader kept in a variable is not freed. Close it, or read with something that lets others write meanwhile: `Get-Content`, Node, or a `FileStream` opened with `FileShare.ReadWrite` and `Delete`.
- **Git Bash** is found as Claude Code finds it: `CLAUDE_CODE_GIT_BASH_PATH`, then `Git\bin\bash.exe` under Program Files, then the Git on PATH. petal starts it with `--noprofile --norc` and its loop, `src\loop.sh`. Requests arrive on standard input; each command runs with `/dev/null` as its input and its output going to a file. The console's code page is UTF-8.
- **Output** comes back up to 30,000 characters, counted as Claude Code counts them (UTF-16 units). Longer output comes back as its first 10,000 and last 20,000 characters, cut at line ends, with a line saying how much is left out, and the reply names the file holding all of it. Bytes that are not UTF-8 become U+FFFD; Windows line endings become `\n`.
- **The reply** ends with a line giving the exit code, the time taken, the shell, the stamen and the folder.
- **Every string petal writes as JSON is valid UTF-8**, a command's own text quoted in a reply and the log's records included: a byte that does not begin a valid sequence becomes U+FFFD. A JSON request can carry text that is not UTF-8 (a lone surrogate such as `\ud800`), and Zig's JSON writer would write such a string as an array of byte values, which no client reads as text.
- **Output a program writes straight to the shell's own output**, not to the command's, is reported in a note on the reply. After each command the loop writes a marker there, so each reply reports what came before its command's marker and nothing after.
- **A timeout** ends the command, its shell and everything it started. The reply is an error and says so; the next command in that shell starts a fresh one in the same folder. The timeout counts from when petal sends the command to its shell. Before that, petal may end a shell that died (waiting up to 5 s) and start a fresh one (waiting up to 60 s for it to report ready). In Bash it also runs its checks, which can wait up to 10 s each: `bash -n`, the lookup of a deletion's variables, and a `from` copy. In all, at most about 95 s. A shell usually starts in 0.2 to 1 s, and in a few seconds when the machine is busy.
- **A cancelled call** (`notifications/cancelled`) is ended the same way and gets no reply, as MCP requires.
- **Progress**: when a call carries a progress token, petal sends progress every 10 seconds while the command runs.
- **The shell and everything it starts run in a job object** that ends them all when the shell is ended or petal exits. A program a command leaves running in the background keeps running while its shell does, and ends with it: at a timeout, a restart, an idle stamen's end, or the end of the session.
- **The shells' environment** is petal's own, which Claude Code gives it, with three changes: `PWD` and `OLDPWD` are removed, so Bash works out its own folder; `POWERSHELL_TELEMETRY_OPTOUT=1`; and `CLAUDE_CODE_EXECPATH` names the executable of the Claude Code that started petal, as Claude Code's own Bash tool does, so `claude` in a petal shell runs that Claude Code. petal finds it as its parent process, when that is a `claude.exe`: Claude Code starts its MCP servers itself, and gives them no `CLAUDE_PID`, though petal reads that first when it is set. petal's loop variables are gone before any command runs.

## The check before running

When the check finds something, petal does not run the command. It answers with each finding and its line, and the agent fixes the command or sends it again with `intended: true`.

- **Commands that do not parse**, by each shell's own parser: PowerShell's, and `bash -n` (Git's `usr\bin\bash.exe`) for Bash.
- **A deletion whose target is built from a variable**: the finding shows what the target resolves to now, names any variable that is empty, and names any variable the command itself sets, whose value cannot be known before it runs. A target that would need code run to work out (`$(...)`) is reported as such. Reading a variable's value has no side effects.
- **A deletion by relative path**: the finding shows the absolute path it resolves to from the shell's folder, and warns when the command also changes the folder.
- Deletions are `Remove-Item` (and its aliases), `cmd /c del|erase|rd|rmdir`, `[IO.File]::Delete` and `[IO.Directory]::Delete` in PowerShell, and `rm`, `rmdir` and `unlink` in Bash.
- **In Windows PowerShell 5.1 only:** double quotes inside an argument to a program, which 5.1 removes; `Out-File`, `Set-Content`, `Add-Content` and `Export-Csv` without `-Encoding`, `Tee-Object -FilePath` and file redirections, which write UTF-16 or the ANSI code page; and `Get-Content` without `-Encoding` in a command that writes, which corrupts a UTF-8 file's non-ASCII characters on the way back.
- **In both PowerShells: a read of a Claude Code transcript that keeps other programs from writing to it, by a .NET reader, `Copy-Item` or `Get-FileHash`.** Claude Code adds to a session's transcript as the session goes on. When an addition cannot be written it tries once more at once, then gives it up (`$fe` and `drainQueuesOnce` in Claude Code 2.1.286). It marks each message written when it queues it (`appendEntry`), so it does not offer a given-up message again until the session's next compaction: the cleanup after a compaction empties those marks (`clearSessionMessagesCache`), and before the compaction boundary is recorded, the conversation up to the newest message the compaction keeps is recorded again, which appends every such message the file lacks, and nothing is recorded again when the compaction keeps no message (`flushBeforeCompactBoundary`; read for a session run through Claude Code's SDK, as the desktop app runs its sessions). So everything Claude Code adds while such a reader holds the file is missing from the transcript until the session's next compaction, and lost if that compaction keeps no newer message or the session ends first, since the messages are held only in the running process (read in the code, not tested). On 2026-10-02, 50 minutes of one session's records went missing this way and came back about 11 hours later, at that session's compaction.
  - The transcripts are the `.jsonl` files under the `projects` folder of Claude Code's configuration folder: `CLAUDE_CONFIG_DIR` when that is set, `.claude` in the home folder otherwise.
  - The readers: `[IO.File]::ReadLines`, `ReadAllLines`, `ReadAllText`, `ReadAllBytes` (and their `Async` forms), `OpenRead`, `OpenText` and `Copy`; `[IO.File]::Open`, `OpenHandle` and `[IO.FileStream]::new` or `New-Object IO.FileStream` unless their share argument allows writing; `[IO.StreamReader]::new` or `New-Object IO.StreamReader` given a path; and `switch -File`. Measured on 2026-10-03, each of these refused appends while it held the file, even a whole-file read lasting a fraction of a second: in both shells, all but the `Async` forms and `OpenHandle`, which exist only in PowerShell 7 and were measured there. `Get-Content`, `Select-String`, and a `FileStream` or `OpenHandle` that shares `ReadWrite` did not. The finding suggests those instead.
  - The cmdlets: `Copy-Item` (and its aliases) and `Get-FileHash`, given a transcript by `-Path` or `-LiteralPath`, a `-Path` wildcard included, matched against what the folder holds then; and `Copy-Item -Recurse` of a folder that holds transcripts. Measured on 2026-10-03 in both shells: each refused appends while it read. Their finding suggests a `FileStream` that shares `ReadWrite, Delete`, copied into the new file with its `CopyTo` method or hashed through `Get-FileHash -InputStream`; measured the same day in both shells, both let every append through and give the same copy and hash. `Get-FileHash -InputStream` is checked where its stream is opened, and a `Copy-Item -FromSession` reads on another computer.
  - Which file is read is worked out without running code: from literal text, variables the shell holds (a list of paths included), environment variables, a variable the command sets once with `=` before reading it, a `foreach` loop's variable from the list the loop runs over, lists of these, and `+` joins of them. A file found only as the command runs, a file piped to a cmdlet among them, is flagged when the command names a `.jsonl` file or the transcripts' folder. A `.jsonl` written as regex text (`\.jsonl`) names no file; a path into the transcripts' folder that goes on to name a file of another kind, such as a memory's `.md`, does not count as naming the folder; and a path whose fixed end names another extension is not a transcript.
  - Not recognized: a transcript reached by another name for the same folder (a short 8.3 name, a link); and a variable the command sets another way, such as `Set-Variable` or `-OutVariable`, which is read at the value it holds before the command runs. A `FileStreamOptions` argument is not read, so a call given one is stopped whatever share it sets.
- **What it cannot catch:** a command that is well formed and does exactly what it says, when what it says is wrong; and what a script or program the command runs does, since the check reads only the command itself. Bash's check is the weaker one: Bash cannot hand over a command's structure, so a small reader in `src\bashcheck.zig` splits the command into words.

## Messages from the user

A UTF-8 text file ending in `.msg` in the session's `inbox\` folder rides on petal's next reply, after a line saying when it was written. Messages come oldest name first and each is moved into `inbox\delivered\`. Write a message under another name first, then rename it to `.msg`, so petal never reads half of one.

## Where things are

- **Data folder:** `PETAL_DATA_DIR` when set, else `%USERPROFILE%\.petal`, which is the same folder from inside the app and outside it. Not `%LOCALAPPDATA%`, for this reason. Started by the Claude desktop app's Claude Code, petal runs inside the app's Windows package. A folder it creates under `%LOCALAPPDATA%` is kept in the package's own folder, `%LOCALAPPDATA%\Packages\Claude_<id>\LocalCache\Local\`. A program outside the app, such as Explorer or a console, finds it only at that path, and it goes with the app's package if the app is removed. Builds before 2026-10-02 used `%LOCALAPPDATA%\petal`, so the sessions they served keep their data there.
- **Per session:** `sessions\<session id>\`, where the session id is `CLAUDE_CODE_SESSION_ID`. Claude Code may start petal more than once in one session, for example around an app update, and every petal of the session writes to the same log. Each one's records begin with a `session started` record carrying its process id, and a petal that is killed ends without a `session ended` record. It holds `log.jsonl` (one record per line, each with its local time and UTC offset), `outputs\<n>.txt` (each command's full output) and `inbox\`. These hold the commands and their output, so they stay on this machine.
- **`PETAL_IDLE_LIMIT_MS`** changes the 30 minutes after which an idle stamen ends. The tests use it.

## The hook

`petal.exe hook` is a PreToolUse hook for petal's own tools. Claude Code gives a hook `agent_id` only for a call made inside a subagent. The hook writes that id, or `main`, into the call as `agent`, with `agent_type` for a subagent, overwriting whatever the call held there. Whatever goes wrong, it prints nothing, which leaves the call as it was.

## Build, test, install, register, update, remove

```
cd <this folder>
zig build --release
zig build test
node tests\petal.test.js
node tests\broken-copies.js
```

- **`zig build --release`** writes `zig-out\bin\petal.exe` in ReleaseSafe mode, which keeps bounds and overflow checks. `zig-out\` and `.zig-cache\` are build output and safe to delete.
- **`zig build test`** runs the unit tests.
- **`tests\petal.test.js`** runs petal over its own protocol in 21 sections. Section 2 compares commands' output and exit codes with running them in the same shell directly; the others check petal's behavior, several against a control run directly. The sections: the protocol, output and exit codes, carried state, standard input, errors, characters and line endings, long output, stray output, the check, stamens, timeouts, cancellation, progress, messages, restart, the hook, the environment, idle stamens, the session's end, memory, and a file a command leaves open. It uses `tests\child.js` as a program to run, works in a temp folder it removes afterwards, and every deletion it sends targets that folder; the transcripts its check is tested on are in a configuration folder of its own there, named by `CLAUDE_CONFIG_DIR`. 260 checks, about 2 minutes.
- **`tests\broken-copies.js`** builds copies of petal, each with one deliberate defect (68 of them), and runs the sections that cover it: each copy must fail at least one check. A first, unchanged copy must pass them all. It first checks that each defect's text still occurs exactly once in the source, so a defect that no longer applies is reported instead of passing unnoticed. About 35 minutes in all; `--only <name>...` runs some of them, the control included when named, so a run can be split to fit a time limit. A name that matches no copy stops the run, so a misspelled one is never skipped unnoticed.
- **Install:** copy the tested `zig-out\bin\petal.exe` to `bin\petal.exe` in this folder, and compare the two files' SHA-256. Sessions run the copy in `bin\`, so building never touches a program that is running.
- **Register:** two entries, both pointing at `bin\petal.exe` by its full path.
  - The server, at user scope, written by Claude Code's own command: `claude mcp add-json petal '<entry>' --scope user`, where the entry is `{"type":"stdio","command":"<full path to bin\\petal.exe>","args":[],"alwaysLoad":true}`. `alwaysLoad` puts petal's tools in every request instead of behind tool search. Pass the entry from a script file, or from a program that quotes arguments for Windows itself, such as Node's `child_process`. Typed into Claude Code's Bash tool, each `\\` in it reaches the program as `\` (Claude Code 2.1.284; Git Bash running the same line from a file passes it intact), and the entry then fails Claude Code's check as "Invalid configuration: : Invalid input". `claude mcp get petal` then starts petal and says whether it connects.
  - The hook, in `~\.claude\settings.json` under `hooks.PreToolUse`: `{ "matcher": "mcp__petal__run|mcp__petal__restart", "hooks": [ { "type": "command", "command": "<full path to bin\\petal.exe>", "args": ["hook"], "timeout": 10 } ] }`.
- **Update the installed copy** while sessions run it: Windows refuses to overwrite or delete a program file that is running, but allows renaming it. Copy the new build into `bin\` under a temporary name and compare its SHA-256 with the tested build's. Rename `bin\petal.exe` to a name of its own, such as `bin\petal.<first 8 hex digits of its SHA-256>.exe`, so that a second update never meets the first's leftover. Rename the copy to `petal.exe`. Delete the old file once no petal process runs it: each session's petal keeps the copy it started until that session's Claude Code restarts, and new ones start the new copy.
- **Remove:** `claude mcp remove petal -s user`, delete the hook's entry, then the data folder, and any data older builds left in `%LOCALAPPDATA%\petal` (from outside the app, at the package path above).

## What to know

- **Claude Code ends an MCP tool call that sends "no response or progress"** for `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` milliseconds: 30 minutes by default for a stdio server, more when the server's entry has a larger `timeout`. It asks for progress on every call, and petal sends it every 10 seconds, so a long command's call stays alive up to the command's own timeout. Its overall limit for a call is 100,000,000 ms by default (Claude Code 2.1.284).
- **petal's shells are separate from Claude Code's own Bash and PowerShell tools.** A `cd` in one is not seen by the other.
- **A Stop gate that attributes file writes to petal calls** can only count a call as running up to some margin after its start plus its timeout, and for a call that names no timeout it must assume petal's default. One built against petal uses a 2-minute margin and the default of 600,000 ms. So the waits before the send (above) must stay well inside that margin. A change that lengthens them, or that changes the default timeout, must be told to whoever keeps such a gate. A program a command leaves running in the background ends only with its shell (above), so it can still write after such a window has closed.
